# Build plan: appointments + AI admissions assistant

Read first: [BUILD_PLAN.md](BUILD_PLAN.md) section 0 (ground rules) and "Admin UI". Those rules apply unchanged.
Module keys, permissions and roles already exist (`appointments`, `aiBot`; `appointments:read|write|manage`, `bots:read|manage`). Do not edit `contracts/*`.

## Research summary (what drives the design)

Sources are mostly vendor pages; treat numbers as unverified. What is solid enough to design on:

| Finding | Design decision |
|---|---|
| Education schedulers (OpenEduCat, Pickatime, uOttawa portal) give each appointment type its own duration, buffer, minimum notice, booking horizon, cancellation window, intake questions and staff assignment; students can cancel and join a waiting list | `AppointmentType` carries all of these; `WaitlistEntry` exists |
| Round-robin / collective routing is a standard team feature | `assignment: 'specific' \| 'round_robin'`; round-robin = least booked in the next 7 days, tie -> lowest id |
| Booking flow should take 30-60 s; set no-show and cancellation policy up front | Public booking form = 4 fields + consent; policy text shown on the page and in the confirmation |
| Reminders reduce no-shows (randomised trials, SMS and calls). A 2012 meta-analysis found no significant difference between 24/48/72 h. Evidence that WhatsApp beats SMS, or for exact timing, is weak and mostly vendor | Reminder offsets are **configurable per type** (default 24 h + 2 h), no claim of superiority. Reminder reply "can't come" lets the slot be released and offered to the waitlist |
| Indian admission bots: instant first reply, FAQ on courses/fees/eligibility, qualification (course, stage, budget, timing), scoring, multilingual, hand-off to a human, push to CRM. No independent evidence of conversion uplift | Bot does exactly these; success is measured with our own funnel (handoff rate, booking rate), not assumed |
| Main risks: hallucinated fees/deadlines, privacy and retention of student chats, RAG poisoning / prompt injection | Answers only from the organisation's own college data; fee/deadline questions are answered from a tool result or declined; conversations are minimised, retained for a limited time, and user text is never treated as instructions |
| DPDP Rules 2025: verifiable parental consent under 18; tracking/behavioural monitoring of children restricted; no chatbot-specific rule found | Under-18 detected in chat -> bot asks for guardian details and consent before collecting more; **no behavioural profiling or ad targeting from chats**; qualification data is only what the student typed; AI disclosure in the first message; legal review listed in GO_LIVE_CHECKLIST |

## Module A: `appointments`  (key `appointments`, folder `src/product/modules/appointments`)

**Models (tenant DB):**
- `AppointmentType` {name, description, mode 'phone'|'video'|'in_person', durationMin, bufferBeforeMin, bufferAfterMin, minNoticeHours (default 2), maxAdvanceDays (default 30), slotStepMin (default 15), capacity 1, assignment, counsellorIds[], intakeQuestions[{key,label,required}], cancellationNoticeHours (default 4), policyText, reminders[{offsetMin, channel 'whatsapp'}], publicBookable, active, locationOrLink?}.
- `WorkingHours` per counsellor {counsellorId, timezone 'Asia/Kolkata', weekly[{day 0-6, ranges[{start 'HH:MM', end}]}]} and `TimeOff` {counsellorId, from, to, reason}.
- `Appointment` {typeId, counsellorId, start, end (UTC Date), status 'booked'|'confirmed'|'completed'|'cancelled'|'no_show'|'rescheduled', who {leadId?, studentId?, name, phone, email?}, answers, source 'staff'|'public'|'bot'|'portal', cancelReason, cancelledBy, rescheduledFrom?, notes, reminderState[{offsetMin, sentAt?}], manageTokenHash}.
- `WaitlistEntry` {typeId, name, phone, preferredFrom?, preferredTo?, status 'waiting'|'offered'|'booked'|'expired'}.
- Indexes: unique partial (counsellorId, start) for active statuses, so double booking is impossible even under race.

**Pure domain (tested without DB):** `computeSlots({type, hours, timeOff, existing, now, from, to})` returns slots in UTC (IST rules, step, buffers, min notice, horizon, no overlap, past never offered); `pickRoundRobin`; `canCancel(type, start, now)`; `validateTransition` (booked->confirmed|completed|cancelled|no_show|rescheduled; terminal states fixed); `reminderDue(appointment, now)`.

**Endpoints (staff, `appointments:*`, counsellor sees only own):** CRUD appointment types and working hours/time off (manage); `GET /appointments/slots?typeId&from&to&counsellorId?`; `POST /appointments` (staff booking for a lead/student); `GET /appointments?from&to&status&counsellorId&mine=1`; `GET /appointments/:id`; `POST /:id/reschedule`, `/cancel {reason}`, `/complete {notes}`, `/no-show`; waitlist add/list; `GET /appointments/summary` (today, upcoming, no-show rate).
**Public (no login, rate limited, org found by slug exactly like `seoPages`/`publicApi` public routes):** `GET /public/:slug/appointments/types`, `GET .../slots`, `POST .../book {typeId, start, name, phone, email?, answers, consentGiven:true}` -> creates lead if none (via `leads` public API, source 'appointment'), books, returns manage link; `GET/POST .../manage/:token` (view, cancel, reschedule). Token is random, only its hash is stored.
**Reminders without a scheduler:** `runDueReminders(now)` (idempotent, uses `reminderState`) exposed as `POST /appointments/jobs/run-reminders` guarded by a platform job secret (`JOBS_SECRET` env, add to `config/env.ts` + `.env.example`) so cron/pm2 can call it; sends through the `whatsapp` module only via an event/hook (no import): publish `appointment.reminder_due`; the whatsapp module is NOT edited, so also store a followups-visible system activity. Document in RUNBOOK. If a reply "can't come" arrives later it is a documented follow-up, not built now.
**Events:** publish `appointment.booked|cancelled|rescheduled|completed|no_show` (append to `DomainEvents`). `registerEvents`: on `appointment.booked` for a lead, move nothing automatically but create a followups-visible activity via the events bus (the followups module subscribes; do not edit it - publish and add a system activity through the existing public API if it exists, otherwise skip and document). On cancel, offer the freed slot to the first matching waitlist entry (mark `offered`, audit).
**DPDP:** consent stored on public bookings; a booker under 18 (asked in intake) requires guardian name+phone; export contributor `student.export` (their appointments); erase listener on `student.erased` anonymises their appointments.
dependsOn: audit, leads (+ students only if you really use it; declare everything you import).

## Module B: `bots`  (key `aiBot`, folder `src/product/modules/bots`)

**Model call:** use the official `@anthropic-ai/sdk` (add to package.json). Model id comes from env `AI_MODEL` (default `claude-opus-5-5`; the owner can later set `claude-haiku-5-5` for cost) and `ANTHROPIC_API_KEY` (optional; module reports `configured:false` and the bot says it is offline when missing). Rules from the Claude API guide: tools with `tool_choice` auto only (forced tool_choice is rejected on current models), no prefill, no `temperature/top_p/top_k`, use `thinking: {type:'adaptive'}` with `output_config.effort` low/medium, check `stop_reason` (`refusal`, `max_tokens`) before using content, pass `fallbacks` only if the SDK version supports it. Put the SDK behind a tiny `LlmClient` interface (`complete({system, messages, tools}) -> {text, toolCalls, usage, stopReason}`) in `infrastructure/`; tests inject a fake. Meter cost with `getPlatform().recordUsage(tenantId, {category:'ai', amountPaise})` computed from `usage` and a configurable per-million-token price table in `domain/pricing.ts`.

**Grounding (the hallucination defence, domain + application):** the bot has NO free knowledge of fees, deadlines or eligibility. It gets read-only tools: `search_colleges`, `get_course_details` (colleges public API: `listActiveColleges`, `getCollege`, `getCourse`; if a needed function is not exported, use what exists and document the gap, do not edit `colleges`), `get_available_slots` and `book_appointment` (appointments public API, see contract below), `capture_lead`, `request_human`. System prompt rules: answer fees/dates/eligibility only from tool results and quote them; otherwise say a counsellor will confirm; never promise admission or scholarship; never ask for Aadhaar, OTP, passwords, card or bank details; disclose it is an AI in the first message; reply in the student's language (Hindi/English/Hinglish); keep to counselling topics.
**Prompt-injection defences:** student text and tool results go only in `user`/`tool_result` content, never concatenated into `system`; tool results are JSON, wrapped with a note that they are data; tool arguments are validated with zod; the bot can never call a tool outside the list, cannot read other students' data (tools take the current conversation's tenant, never a tenant id from the model); output is length capped and stripped of anything that looks like a secret.
**Models:** `BotSettings` {enabled, name, greeting, languages[], handoffKeywords[], workingHoursNote, qualification fields enabled, publicChannelEnabled, retentionDays (default 90), dailyMessageCap, monthlyBudgetPaise}; `Conversation` {channel 'web'|'whatsapp'|'staff_test', visitorTokenHash, leadId?, status 'open'|'handed_off'|'closed', language, qualification{course?, stage?, budgetBand?, city?, percentage?, timeline?}, score 0-100, scoreReasons[], messages[{role,text,at,toolSummary?}], handoff{at, reason, assignedTo?}, consent{given,at}, minor{suspected, guardianConsent}, tokens{in,out}, expiresAt (TTL index from retentionDays)}.
**Qualification score (pure domain, tested):** deterministic points from typed answers (course chosen, percentage known, budget stated, timeline within 3 months, phone verified by booking, asked for counsellor) -> `hot|warm|cold`; reasons listed. The LLM extracts fields via the `capture_lead` tool; the score is computed in code, not by the model.
**Flows:** (1) public web widget endpoint `POST /public/:slug/bot/message {visitorToken?, message}` (rate limited per IP and per visitor, org by slug, consent line shown on first use, message length cap 1000); (2) staff test console `POST /bots/test`; (3) WhatsApp inbound: subscribe to the existing whatsapp inbound event if one exists (check `whatsapp` module and `DomainEvents`); if there is none, expose the same service behind `POST /bots/whatsapp/inbound` guarded by an HMAC secret and document wiring as pending. (4) Handoff: keyword, low confidence, frustration, a request for a human, a minor needing guardian, or a failed/refused model call -> status `handed_off`, create/update the lead (`leads` public API), assign via `getPlatform().listTeam` round-robin of `counsellor` role (or the appointments assignment if booking), publish `bot.handoff` and `bot.lead_captured`.
**Staff endpoints (`bots:read|manage`):** settings get/put; conversations list/filter (status, score, channel, date) and detail; `POST /bots/conversations/:id/takeover|close`; `GET /bots/summary` (conversations, leads captured, handoff rate, bookings via bot, cost); `POST /bots/purge` (delete expired now); export/erase contributors for the student (conversations tied to a lead/student).
**Privacy:** store only what is needed; phone/email in messages masked in the stored transcript when not already a lead field; never send other leads' data to the model; Anthropic is a sub-processor (note in docs/GO_LIVE_CHECKLIST: DPA, 30-day retention, DPDP notice text).
dependsOn: audit, leads, colleges, appointments (only if you import it; do).

### Contract bots can rely on from appointments (`appointments/index.ts` must export exactly)
```ts
listBookableTypes(tenantId): Promise<{ id:string; name:string; mode:string; durationMin:number }[]>
getAvailableSlots(tenantId, input:{ typeId:string; from:Date; to:Date; counsellorId?:string }): Promise<{ start:Date; end:Date; counsellorId:string }[]>
bookAppointment(tenantId, input:{ typeId:string; start:Date; name:string; phone:string; email?:string; answers?:Record<string,string>; leadId?:string; source:'staff'|'public'|'bot'|'portal'; consentGiven:boolean }): Promise<{ id:string; start:Date; end:Date; counsellorId:string; manageToken:string }>
```
The appointments agent builds these first; the bots agent codes against them and integrates for real once they exist.

## Admin UI (repo `../counsellor-platform-admin`)
- `src/modules/appointments`: pages Calendar/list (today, week; status filters; actions book/reschedule/cancel/complete/no-show), Appointment types (form with all fields and plain-language help), Availability (weekly hours + time off per counsellor), Waitlist. Nav section "Counselling", perms as above, `module: 'appointments'`.
- `src/modules/bots`: pages Conversations (list + transcript view with score, handoff, take over), Bot settings (enable, greeting, languages, handoff words, retention, budget, API key status), Test console, Summary. `module: 'aiBot'`.
- Public pages are out of scope for the admin (they are API endpoints; widget/page snippet shown in the settings page as copy-paste HTML using `PUBLIC_BASE_URL`).
- Strings: add keys to `src/shared/i18n/translations` en and hi for nav + page titles only (same scope as existing).
